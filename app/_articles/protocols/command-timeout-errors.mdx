A command timeout means the app or hub did not receive a response quickly enough. It does not always mean the lock failed to move. Sometimes the lock completed the action, but the confirmation message was delayed or lost.

That ambiguity is why you should avoid repeated blind retries. If the app says timeout, first check the actual door state when possible. Repeated lock and unlock commands can create confusion, extra motor cycles, and misleading status.

## Common Causes

The most common cause is weak signal. The command has to travel from the app or hub to the lock and then return with status. Poor Wi-Fi, a weak Zigbee or Z-Wave mesh, too many hops, or interference can push that round trip beyond the platform timeout.

Low batteries are another common cause. A weak battery can still power the keypad, but the motor may move slowly and the radio may respond poorly. Door alignment can create the same symptom when the motor struggles to throw the bolt.

The lock can also be busy. Auto-lock, calibration, a previous command, or a firmware update may make a new command wait long enough to time out.

## First Checks

Start with the physical door. If you are nearby, see whether the lock is actually locked or unlocked. Then test the keypad or thumb turn. If local operation is slow or rough, fix batteries or alignment first.

Next, check whether the app shows the lock online. If it is offline, use [Smart Lock Keeps Going Offline](/articles/protocols/smart-lock-keeps-going-offline). If it is online but commands are slow, focus on signal quality and motor load.

Replace weak batteries with a fresh matched set before spending time on deeper network troubleshooting. Then test again with the door open and closed. A timeout only with the door closed points toward alignment.

## Improve The Signal Path

For Wi-Fi locks, check 2.4 GHz coverage at the door. Move the router or add a better access point if the signal is weak. For Zigbee, Z-Wave, or Thread locks, add a powered repeater or router device between the hub and the lock.

After adding or moving infrastructure, give the network time to rebuild routes. Wake the lock from the keypad and test several commands. For broader guidance, use [Improve Connection Stability](/articles/protocols/improve-connection-stability).

## Reduce Command Conflicts

Avoid sending multiple commands while the lock is still moving. Wait for the motor to stop and the app to refresh before retrying. If auto-lock is enabled, temporarily disable it while troubleshooting so it does not overlap with manual testing.

If a command times out during calibration, firmware update, or pairing, wait. Interrupting those processes can create worse problems than the timeout itself.

## When To Reboot

If the lock is responsive locally but the app keeps timing out, restart the hub, bridge, or router before removing lock batteries. For a battery lock, power cycling should be a later step, not the first one.

If the lock becomes fully unresponsive, use the physical key or backup access method, then remove and reinsert batteries. After it boots, test local operation before testing app control.

## Final Verification

After each fix, run several commands from the app and one from the keypad. Confirm the app status matches the real door. If timeouts continue after fresh batteries, smooth alignment, and better signal, update firmware and contact manufacturer support with the exact error, lock model, hub, and when the timeout occurs.

Timeouts are usually a symptom, not the root cause. Fix the signal path, battery state, and mechanical load, and the app usually becomes reliable again.
